# ADR-029 : Migrations et schémas de la base

- **Statut :** Décidé le 24 novembre 2026.

## Contexte

L'ADR-008 retient PostgreSQL et des migrations Flyway, et laisse ouverte la question « schéma par module ou schéma unique ». L'ADR-022 impose que chaque module possède ses tables, sans jointure entre modules. Sept modules, plusieurs auteurs : il faut dire où se rangent les migrations et comment elles sont numérotées.

## Décision

Un schéma PostgreSQL par module, nommé comme le module (minuscules, chiffres et `_`). Les migrations d'un module sont dans `db/migration/<module>/`, nommées `V<n>__<description>.sql`, avec un entier `n` propre au module. Un Flyway par module, dont l'historique (`flyway_schema_history`) est dans le schéma du module ; la classe `MigrationsParModule` du noyau commun les applique au démarrage, dans l'ordre alphabétique des modules, et la configuration automatique de Flyway dans Spring Boot est désactivée. Un module sans migration ne crée aucun schéma.

Règles : une migration appliquée ne se modifie jamais (on en ajoute une) ; toute migration passe par une pull request ; aucune clé étrangère ni jointure entre schémas (ADR-022) ; les agrégats Spring Data JDBC portent `@Table(schema = "<module>", value = "...")` et le SQL explicite qualifie ses tables par le schéma (ADR-028).

## Preuves

- Flyway exige une version unique pour chaque migration versionnée [120]. Le schéma par défaut est celui qui contient la table d'historique ; en mode multi-schémas, elle y est placée [121, 122, 123]. Un article de Redgate (2021) présente un historique séparé par schéma comme le choix recommandé, et déconseille un historique partagé [126].
- Essai du 24 novembre 2026 sur PostgreSQL 18, avec un seul historique commun et des blocs de versions par module (10 pour l'un, 20 pour l'autre) : la version 10.2 ajoutée après la 20.1 déjà appliquée est refusée (« Detected resolved migration not applied to database »), car `outOfOrder` vaut `false` par défaut [124] et la validation est active par défaut [125]. Avec `outOfOrder=true`, elle est appliquée. L'essai était un test jetable, non conservé.
- Avec un Flyway par schéma, la même situation ne pose aucun problème : le test `uneMigrationAjouteeDansUnModuleNeBloquePasLesAutres` ajoute `V2` à un module après `V5` dans un autre. Les autres tests de `MigrationsParModuleTest` vérifient : même numéro de version dans deux modules accepté, deux fichiers de même version dans un module refusés, migration modifiée après application refusée (somme de contrôle), nom de dossier invalide refusé, aucun schéma créé sans migration.
- Spring Data JDBC : l'attribut `schema` de `@Table` est dans la Javadoc [127, 128] et pas dans le guide ; `SchemaParModuleTest` enregistre et relit un agrégat dans un schéma de module après exécution des migrations au démarrage.
- Un schéma n'isole pas : « les schémas ne sont pas rigidement séparés », l'accès dépend des privilèges [118, 119]. Essai : le même utilisateur lit deux schémas dans une seule requête.

## Conséquences

Les frontières entre modules restent garanties par `ModularityTests` et par la convention, pas par la base ; le schéma les rend visibles (`referentiel.competence`). Une isolation réelle demanderait un rôle de base par module avec des privilèges par schéma [118, 119] : non prévue. Chaque module avance à son rythme, sans règle de blocs de numéros ni `outOfOrder`. Deux auteurs d'un même module peuvent choisir le même numéro : le test `lesMigrationsDuDepotSAppliquentSurUneBaseVide` échoue alors en CI (« Found more than one migration »), et le second renumérote avant la fusion. Une migration de numéro inférieur fusionnée après qu'une autre a été appliquée sur une base de développement est refusée par Flyway sur cette base : repartir de zéro (`docker compose down -v`) ou renuméroter. La configuration de Flyway n'est plus celle de Spring Boot (propriétés `spring.flyway.*`, point d'accès de supervision) : à revoir au changement de version du cadre (ADR-020). Seules les migrations en SQL sont découvertes.

## Points non vérifiés

La documentation de Flyway ne dit pas explicitement si la validation échoue sur une migration « ignorée » : l'échec est constaté par l'essai, pas lu. La documentation de Spring Boot sur plusieurs instances de Flyway n'a pas été lue. Les tables de Spring Batch (ADR-009) et du registre d'événements de Spring Modulith restent dans le schéma `public` : leur emplacement est à décider avec le lot 4. Aucune restauration ni retour arrière de migration n'a été essayé.

## Alternatives

Un schéma unique, un seul Flyway, des blocs de versions par module et `outOfOrder=true` (plus simple, mais l'ordre d'application peut différer d'une base à l'autre) ; un schéma unique avec des préfixes de noms de tables ; un rôle de base par module (isolation réelle, coût d'administration).
